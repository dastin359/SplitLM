# SplitLM: NPU prefill + CPU decode with custom kernels on Snapdragon X SoC

LLM inference on a Snapdragon X laptop, rebuilt around what each chip is good at, with each phase pushed toward its hardware ceiling. Two halves:

- **A phase-split engine.** Long prompts are prefilled on the Hexagon NPU, whose matrix unit prefills about 4× faster than the CPU or GPU here. Tokens are decoded on the Oryon CPU, which reads memory fastest. The model state moves between them through shared memory (about 7 ms for a 512-token prompt). For models too big to hold twice (MoE experts, dense models over 6 GiB), both chips work from one copy of the weights. Concurrent requests overlap: the NPU prefills while the CPU decodes a batch. OpenAI-compatible server and live dashboard.
- **Kernels pushed toward the hardware ceiling.** Fused NPU element-wise kernels, a faster MoE expert matmul and causal block skipping in NPU flash attention: Qwen3.5-2B NPU prefill +26% over stock llama.cpp kernels, LFM2.5-24B-A2B +21%. On the CPU: kernels that decode straight from the NPU's tiled weights, in-place recurrent state (+5% decode), and speculative decoding with the model's own MTP head (Qwen3.8-27B 1.97× on the CPU, identical text).

**On Qwen3.5-2B, a 4K-token request is about 2× faster than llama.cpp's default device choice and 1.6× faster than its fastest single chip, from the same build. NPU prefill runs at 1.2× Qualcomm's own GenieX runtime on this laptop, with the same model file.**

Built in a day on a Dell Latitude 7455 (Snapdragon X Elite X1E80100, 32 GB LPDDR5x-8448, Windows 11 on Arm), on a fork of llama.cpp.

## Results

### What the split buys

Qwen3.5-2B Q4_0, one request with a 4096-token prompt and 128 generated tokens. Every row uses the same SplitLM build (same kernels), so the table isolates the effect of splitting the phases across chips:

| Setup (same build) | Prefill | Decode after 4096 tokens | First token | Whole request |
|---|---|---|---|---|
| llama.cpp default device choice | 725 t/s | 31.4 t/s | 5.65 s | 9.72 s |
| CPU only | 423 t/s | 55.4 t/s | 9.69 s | 12.0 s |
| NPU only | 1,614 t/s | 29.0 t/s | 2.54 s | 6.95 s |
| **SplitLM: NPU prefill, CPU decode** | **1,614 t/s** | **55.4 t/s** | **2.54 s** | **4.85 s** |

Rates are llama-bench at 4096 tokens (NPU with the engine's 1024-token batches); first-token and whole-request times are computed as prompt ÷ prefill + 128 ÷ decode. The split is 2.0× the default device choice, 2.5× CPU only and 1.4× NPU only. The SplitLM row assumes decode after the handoff runs at the CPU-only rate; an interleaved study later found no decode deficit after the handoff (see Limitations). Measured end to end in that run: first token in 2.10 s vs 8.27 s CPU-only and 2.06 s NPU-only; whole request with 128 tokens about 5.1 s vs 10.9 s CPU-only and 6.4 s NPU-only.

**Eighteenth round** (correctness): the rare LFM2.5 prefill deviation was narrowed to one step of the streamed expert gate/up kernel. Re-running the op on identical inputs sometimes gave a different result, always in the step that DMA-gathers the next segment's activation rows while the previous item's output is scattered; the wrong data was usually one 128-byte output-tile vector. Running the scatter before the gathers removed it in the repeated-op check (0 in 1,105 against 6 in 1,190 with the old order, one-sided p ≈ 0.02), with identical results and no speed change. Whether it also removes the natural one-in-1,000 prefill deviation is not yet shown (see Limitations).

**Seventeenth round** (robustness): NPU ops now run on a 64 KB stack instead of the ~16 KB DSP callback stack, which had as little as 0-1.6 KB left; results and speed are unchanged. The rare LFM2.5 n-gram speculative-decoding text flips were traced to the NPU prefill, not the CPU: about 1 prefill in 1,000 hands the CPU a slightly different state, starting in the streamed expert gate/up kernel, and a near-tie later turns that into different text. Its cause is not found yet (see Limitations).

**Sixteenth round** (correctness): the rare 8-bit-activation perplexity deviation was a race in the NPU's shared HVX work queue. A worker that sat out one task and stalled between two loads could run its share of the next task twice and release the producer early, so a second copy of its work read buffers that were already being reused. Only the int8 paths issue tasks for fewer than four threads just before four-thread tasks, which is why it only showed up there. A test switch that widens the race window confirms it: the old scan gives about 1 event per 200 iterations with the switch, the fixed scan none. Without the switch the fixed build ran ~129K stress iterations and 42 full 8-bit-activation perplexity passes with no deviation. Speed is unchanged. The round's speed track (reordering, packing and mixing LFM2.5 expert work items, a lookup-table SwiGLU scatter, non-temporal stores) was 3-5% slower in every variant; it found that the matrix unit itself slows down when the vector threads put more traffic on the on-chip memory at the same time, which our pipeline models had ignored.

**Fifteenth round** (correctness): the run-to-run variation of Qwen3.5-2B perplexity at `-c 4096 -ub 1024` turned out to be a real bug. In one batch the memory allocator placed the fused gate/up + SwiGLU output on top of the activation the kernel was still loading by DMA, so the result depended on timing (PPL 13.08 instead of 11.07 on 8 chunks; now 11.0671 on every run, and a 2-chunk reproducer gives 30/30 identical runs). Such fusions are now refused, which changes nothing on the benchmark shapes (speed flat, every other perplexity hash identical). The flash-attention op-test hash differences came from the test, whose attention mask ignored the seed. The rare 8-bit-activation deviation is narrowed to one dense matmul following attention (about 1 event per 4-9K iterations in an op-level reproducer) but not fixed. The round's speed track, persistent dequant workers feeding a ring of weight tiles for LFM2.5's experts, was 2.6-13% slower on the op in every configuration: deeper rings do not fit next to the activation buffers in the 8 MB VTCM without smaller chunks, and smaller chunks add more work than the lookahead saves. A diagnostic bounds the expert scatter's DDR store traffic at 6.3% of the op.

### Speculative decoding in the server

`trilane-server` drafts with the model's own MTP head when the GGUF has one (Qwen3.5 / Qwen3.8). `--spec off` or `TRILANE_SPEC=0` turns drafting off and runs exactly the previous code path (kernels and KV layout included); models without an MTP head always take that path. Per decode step every slot drafts k tokens (the MTP passes are batched over the slots), then the target model verifies all slots' `cur` plus k drafts in one decode call, each slot keeps the longest drafted prefix its own sampler reproduces from the target logits (llama.cpp's sample-and-match rule, so sampled requests keep their distribution), and the rejected positions roll back through per-slot recurrent-state snapshots. The draft length depends on how many slots decode (`--spec-k 3,1,0`: 3 drafts with one slot, 1 with two, none from three on; `--spec-k auto` picks it online from measured step times). A slot near the end of its context caps the step's draft length, so every slot's tokens fit its KV stream. The MTP head catches up on the last 1024 positions of a slot only (`TRILANE_MTP_WINDOW`): replaying a long prompt, or a long draft-free stretch with 3-4 slots, through the MTP layer cost more than it gave (2B, 3.8K-token prompt: 55.0 t/s with the full catch-up, 73.2 with the window, acceptance 40% vs 41%).

Greedy output with drafting is identical to plain decoding, per request, at 1, 2 and 4 concurrent requests, and sampled requests (temperature 0.8, fixed seeds) produce identical text too. That needed batch-invariant CPU kernels, which the server switches on together with drafting: the K-quant matrix-vector and matrix-matrix kernels, the 2×2 i8mm dot kernel and flash attention's split-KV and tiled paths all rounded differently from the one-token path, so a token's logits depended on how many tokens shared its decode call. With `GGML_CPU_BATCH_INVARIANT=1`, K-quant rows go through the 4-row kernel, dot products use the one-row kernel, and attention splits the KV cache into 128-cell chunks at fixed cell indices, each (query row, chunk) on the decode attention kernel, folded in chunk order; so long contexts keep the split-KV parallelism. `trilane-bitcheck` (new) compares one token per call against 2-4 tokens, 2-4 sequences and other thread counts per call, bit for bit, on ~300- and ~3.8K-token contexts: every shape is bit-identical. Each slot also gets its own KV stream, because cells freed by rolled-back drafts were reused out of position order and attention sums cells in cache order. The reference for "identical" is therefore plain decoding with the same kernels (`TRILANE_SPEC=0 TRILANE_BATCH_INVARIANT=1`); with drafting on, multi-slot decoding of these models is deterministic. The previous path is not: a request's greedy text can change with what else is decoding (2B: 2-3 of 4 prompts differ between one-at-a-time and 2 or 4 at once), and `trilane-spec`'s drafted text differed from plain decoding on 2 of 4 new test prompts.

### Against Qualcomm's own runtime

Qualcomm AI Hub's "optimized" Qwen3.5-2B is byte-identical to the GGUF used here (unsloth Q4_0, sha256 `cd70221b…`), deployed with GenieX, Qualcomm's llama.cpp-based runtime. Measured on this laptop with a 532-token prompt, `geniex infer` runs a model on one compute unit chosen with `--compute`: NPU 1,291 t/s prefill and 28.3 t/s decode, CPU 623 t/s prefill and 47.7 t/s decode. SplitLM's NPU prefills ~512 tokens at about 1,600 t/s (1.2× GenieX's NPU) and decodes on the CPU in the same request. AI Hub's published X Elite figures at a 4096-token context are 668 t/s prefill and 4.12 t/s decode; their test conditions are not stated, and GenieX was not measured here at 4096 tokens.

TFLOPS = t/s × 2 × active matmul weights per token (2.75 / 4.38 / 49.45 GFLOP; attention and output head excluded). The ceilings come from measurement, not datasheets: inside a matrix job the NPU sustains 3,809-3,982 FP16 MACs per cycle at 1.40 GHz, which we round up to a 4,096-MAC peak (11.48 TFLOPS); the best DRAM read loop reaches ~110 GB/s (135 GB/s theoretical).

What keeps Qwen3.5-2B below the prefill ceiling: every Q4_0 matmul expands weights to fp16 on the vector units first (the matmuls alone cap near 70%), and the recurrent-state scan and element-wise ops took about 40% of the time (125 of 317 ms per 512-token batch) before the eleventh round made the scan and convolution block about 25% faster; with the same perplexity, its realistic ceiling in this format is now about 66-67%. LFM2.5 is held back mainly by its expert matmuls (the pipelined expert kernel above overlaps its DMA, dequant, matrix-unit and scatter steps; the matrix unit is still idle much of the time) and by attention. Decode's matmul kernels stream at 90-95 GB/s (profiled from an empty context); the rest of the gap is ~785 graph nodes per token with their thread barriers (about 1.3 ms) plus about 2.3 ms per token of attention over the 4,096-token cache (63.4 t/s from an empty context vs 55.4 at 4K).

Other measurements (Qwen3.5-2B, early build with stock NPU kernels): NPU prefill costs 8 mJ per token above a 15.5 W idle vs 90 mJ on the CPU (512-token prompts); CPU decode 0.81 J per token above idle vs 0.20 J on the NPU at half the speed (1.08 vs 0.73 J counting idle). Four simultaneous 400-550-token requests: 79 generated t/s aggregate with NPU prefill and CPU continuous batching; the same engine on the CPU alone reached 55 t/s in an earlier run (older build; not a same-session A/B).

## How it works

```
             prompt tokens                                   generated tokens
                  |                                                 ^
                  v                                                 |
   +-------------------------------+   state handoff    +-------------------------------+
   |  NPU lane (Hexagon v73)       |  KV + recurrent    |  CPU lane (Oryon, 8 threads)  |
   |  llama_context on HTP0        |  state, 7-16 ms    |  llama_context on CPU         |
   |  prefill, ubatch 512 / 4096   | -----------------> |  decode, continuous batching  |
   +-------------------------------+                    +-------------------------------+
                  |                                                 |
                  +---- one weight copy (MoE experts, dense > 6 GiB) ---+
                       Q4_0 tiles in NPU memory; the CPU reads them in place
```

- **State handoff.** After prefill, `llama_state_seq_get_data` snapshots the sequence (attention KV plus the recurrent state of hybrid models) and `llama_state_seq_set_data` restores it into the CPU context: 25 MB and ~7 ms for 512 tokens of Qwen3.5-2B, 16 ms for 1.7K tokens of LFM2.5.
- **One weight copy where memory needs it.** The NPU repacks Q4_0 weights into 32×32 tiles in shared memory. For MoE models (experts) and dense models over 6 GiB, a new CPU buffer type (`CPU_HTPTILE`) points the decode model's Q4_0 tensors at those tiles, and a NEON SDOT kernel reads them in place (CPU reads of NPU memory reach 91-99% of heap bandwidth; the expert kernel streams ~90 GB/s). Small models such as Qwen3.5-2B keep a second CPU copy, because aliased decode is about 7% slower. In `trilane-spec`, a second buffer type (`CPU_SHARED`) lets the decode model borrow the prefill model's CPU-resident head and embeddings (1.6 GiB saved on Qwen3.8-27B).
- **Concurrent engine.** An NPU worker prefills new prompts while the CPU decodes up to 4 sequences in one batch (`--slots N`). A stall-aware router sends a prompt to the CPU when the NPU's fixed cost would dominate. With `--npu-decode-slots 1`, the otherwise idle NPU decodes an overflow sequence and hands it back when a CPU slot frees up.
- **Prefix cache.** The handoff snapshot doubles as a cache entry keyed by the exact prompt tokens, so a follow-up turn prefills only what follows the cached prompt: the previous reply plus the new message (80 tokens and a 0.17 s first token on a 3.3K-token conversation).
- **NPU keep-warm.** After ~1-3 s idle the NPU drops into a low-power state, and the next prefill ran ~2.5× slower on LFM2.5; a 4 KB op every 20 ms keeps it ready.

### Changes to llama.cpp (`patches/`)

- `ggml-hexagon` (NPU): fused element-wise kernels (sigmoid, conv block, norms, residual add in the matmul output), a streamed, pipelined MoE expert matmul (weight DMA overlapped with the activation gather, one gather for gate+up, matrix-unit work overlapped with dequant and scatter), causal key-block skipping in flash attention, and a 64-bit mapping-mask fix. New `test-backend-ops` cases cover the fused kernels, LFM-shaped expert matmuls and causal-mask attention; the mask fix is checked with the existing tests.
- `ggml-cpu`: `CPU_HTPTILE` and `CPU_SHARED` buffer types, NEON kernels over NPU tiles, an i8mm kernel for 2-4-token speculative verification, single-token decode fusions (recurrent-state update + copy, row-split CONCAT) and barrier elision (`GGML_CPU_GDN_CPY_FUSION=0` / `GGML_CPU_BAR_ELIDE=0` disable them), a per-op and per-matmul-shape profiler (`GGML_CPU_PROF=N`), opt-in decode knobs (`GGML_GEMV_NOBAR`, `GGML_REPACK_CHUNKS`, `GGML_GEMV_PF`, default off).
- `ggml-cpu` batch-invariant mode (`GGML_CPU_BATCH_INVARIANT=1`): K-quant rows always through the 4-row gemm, one-row dot kernels, split-KV flash attention with fixed 128-cell chunks for up to 64 query rows, so logits do not depend on how many tokens or sequences share a decode call or on the thread count; `llama_kv_cache` restores a single sequence across caches with different stream counts.
- `llama`: recurrent states read in place instead of copied each step; `llama_model_get_tensor()`; `LLAMA_MMAP_NO_PREFETCH`. `common`: `common_speculative_set_ctx_tgt()`, so speculative decoding can prefill on one context and verify on another.

## The ExecuTorch path

SplitLM runs on llama.cpp's Hexagon backend because it builds natively for Windows on Arm today (ExecuTorch 1.5.1 publishes Windows wheels for x64 only, and its Qualcomm backend compiles models ahead of time with the QAIRT SDK). The design maps directly onto ExecuTorch, and that is the planned port:

- **Two methods, two delegates.** Export the model's prefill method (a 1024-4096-token batch) delegated to the Qualcomm QNN backend on the HTP, and its single-token decode method delegated to XNNPACK on the Oryon CPU. ExecuTorch's Qualcomm llama example already builds separate prefill and KV-cache decode graphs, but runs both on the NPU; our measurements say decode belongs on the CPU (55 t/s vs 29 t/s on the NPU for Qwen3.5-2B at 4096 tokens).
- **State handoff.** Keep the KV cache (and recurrent state for hybrid models) in a shared buffer that both methods use as input and output, the same snapshot/restore that SplitLM does with `llama_state_seq_get/set_data` today.
- **One weight copy.** Our `CPU_HTPTILE` result (CPU reads of NPU memory at 91-99% of heap bandwidth) says the decode delegate can read the NPU's weight buffers in place instead of loading a second copy.
- **Kernel lessons.** Fp16 matmuls with on-the-fly Q4_0 expansion cap near 70% of the HMX peak; QNN's integer (w4a16 / w8a16) matmuls avoid that expansion, which is the route past the ~55% FP16 ceiling measured here.

## How it was built

SplitLM was built in about 16 hours by Claude Code (Claude Opus 5.5) running autonomously overnight under my direction: targets set against measured hardware ceilings, then a fleet of agents in separate git worktrees (NPU kernels, speculative decoding, the MoE expert kernel, attention, decode overhead). Each kernel change was checked with `test-backend-ops`, a same-session A/B run against the previous build, and a greedy-text or perplexity comparison; a multi-agent code review covered the engine and server, and later kernel work also got an adversarial reviewer agent. One NPU and one memory bus were shared by everyone, so a hardware lock serialized the measurements; when the lock failed (a few times overnight), the overlapping runs were discarded and redone. Comparisons across builds or settings are labeled as such.

## Build and run

Requires Windows 11 on Snapdragon X, Visual Studio 2022 Build Tools (ARM64 + Clang), Hexagon SDK 6.6.0.0 (tools 19.0.07), Adreno OpenCL SDK 2.3.2, Windows SDK 10.0.26100 with the WDK (inf2cat, signtool), and test-signing with a trusted self-signed certificate (see `docs/backend/snapdragon/windows.md` in llama.cpp; put the .pfx at `%USERPROFILE%\Certs\ggml-htp-v1.pfx` or set `HEXAGON_HTP_CERT`). Clone both repos side by side in one folder, then run one command per line (PowerShell):

```
git clone https://github.com/dastin359/SplitLM
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
git checkout 848bbda9041decd87904f7eb5a2990863ecce03b
git apply ..\SplitLM\patches\llama.cpp-splitlm.patch
..\SplitLM\scripts\build-llama.bat
cd ..\SplitLM
.\build.bat

cd ..\llama.cpp\pkg-wos\bin
$env:ADSP_LIBRARY_PATH = "$PWD\..\lib"
.\trilane-server.exe -m <model.gguf> --prefill-dev HTP0              # dashboard at http://127.0.0.1:8080
.\trilane-server.exe -m <model.gguf> --prefill-dev HTP0 -ub 1024 --bench 2600
```

`--bench N` runs a ~1.3N-token prompt through the split, NPU-only and CPU-only routes plus a cached follow-up, without HTTP (`-ub 1024` matches the Qwen3.5-2B runs; models over 3 GiB default to 4096-token batches). API: `POST /v1/chat/completions` (OpenAI format, `stream: true` for SSE); an optional `"trilane": {"route": "auto" | "split" | "npu" | "cpu"}` forces a route. `GET /stats` returns routing, cache, slots and per-request timings. The binaries keep the project's working name, `trilane`.

Speculative decoding: `--spec auto|on|off` (default auto: on for GGUFs with an MTP head, e.g. `models/draft/Qwen3.5-2B-MTP-Q4_0.gguf` or Qwen3.8-27B), `--spec-k 3,1,0` (drafts per slot by number of decoding slots, or `auto`), `--draft-head N` (draft head over the first N token ids, default 65536 for 248K vocabularies), `-tb N` (threads of verification batches, default `-t` + 2). `TRILANE_SPEC=0|1`, `TRILANE_BATCH_INVARIANT=0|1` (default: on while drafting), `TRILANE_MTP_WINDOW` (default 1024). `--bench-concurrent N --bench-prompts a.txt,b.txt --bench-route split --bench-mode seq|conc|both` reruns the measurements above; per-request `n_drafted` / `n_accepted` are in `/stats`.

`--prefill-model <file.gguf>` loads a separate GGUF of the same model for the NPU lane (the CPU lane keeps `-m`). `scripts/make-prefill-gguf.py` writes one with the FFN gate/up weights stored as the exact fp16 dequantization of the Q4_0 weights, which skips the HVX dequantization of those matmuls and lets the SWIGLU run in their epilogue. On Qwen3.5-2B (1.93 GiB file instead of 1.12): NPU prefill pp4096 +2.6-3.4% at ub512-2048, split-route TTFT at 4,092 tokens 2.55-2.60 s -> 2.48 s, PPL 13.8503 -> 13.8514, same short greedy text. It needs the llama.cpp change that fuses the SWIGLU only for unquantized gate/up weights. Weight aliasing is off with a separate prefill file, and NPU decode slots get slower with it (21 vs 29 t/s), since they read the larger fp16 weights.

## Limitations

- CPU decode speed varies run to run by up to 2×. A follow-up study (38-42 interleaved requests per session) found no deficit after the NPU handoff: split-route and CPU-route medians match (60.6 vs 58.3 t/s; 56.9 vs 56.3 in a second session), with identical greedy text. The earlier 54.7 vs 63.7 gap came from a platform-wide slow state in which all CPU clusters run at one capped clock; it hits either route. Decode numbers should be measured interleaved and repeated.
- Single-copy aliasing covers Q4_0 weights only, because the CPU tile kernel reads Q4_0 tiles. Other formats the NPU tiles (Q4_1, Q8_0, K-quants, IQ4_NL, MXFP4) keep a separate CPU copy, and formats the NPU cannot run (e.g. IQ3_S) stay on the CPU.
- The server drafts only with an MTP head (Qwen3.5 / Qwen3.8 GGUFs that contain it). No draft model speeds up LFM2.5-24B-A2B: its only tokenizer-compatible small model (LFM2.5-2.6B) reads more bytes per token than the 2B-active target, and drafting on the NPU or GPU slowed CPU decode 17-21% through shared memory bandwidth. Requests that decoded on an NPU decode slot (`--npu-decode-slots 1`) do not draft after they move to the CPU. A prompt restored from the prefix cache drafts from the hidden states of its new tokens only, so acceptance is lower on long cached conversations. Builds before the fifth round give wrong drafted text on Qwen3.5/3.8 unless `LLAMA_RS_NO_IDENT=1` is set.
- `trilane-spec`'s "identical text" results were measured on two prompts; on other prompts its drafted greedy text can differ from plain decoding by rounding (it does not set `GGML_CPU_BATCH_INVARIANT=1`).
- In the server, the "drafting on" text equals plain decoding with the batch-invariant kernels; against `--spec off` (the faster mixed kernels) greedy text can differ by rounding, as that path's text already differs between one request at a time and several at once.
- On dense models too large for two copies (Qwen3.8-27B), decode on the split route matches CPU-only, and speculative decoding in `trilane-spec` is about 2% slower (it gives multi-token verification batches two extra threads by default when the weights are aliased; `-tb` overrides), because the CPU verifies drafted tokens over the NPU's tiled weights.
- Output buffers larger than 512 MiB (full-vocabulary logits for a whole batch, as in `llama-perplexity`) are kept off the NPU once more than 8 GiB of weights are mapped to it (`GGML_HEXAGON_MAX_DST`, `GGML_HEXAGON_MAX_DST_MAPPED`): the NPU maps buffers lazily, and on a long-running machine a 1 GB mapping next to LFM2.5's 12.6 GB of weights could fail inside the NPU and kill its process. Those output layers then run on the CPU (LFM2.5 perplexity unchanged, ~8% slower per pass); normal prefill and decode are unaffected.
- `llama-perplexity` with 2048-token batches fails on Qwen3.5-2B ("op does not fit into empty batch"): a whole batch of full-vocabulary logits (2 GB) does not fit within the NPU's 2 GB mapping limit together with the operation's other buffers. 1024-token batches work.
- The NPU prefill of LFM2.5 is very rarely not bit-for-bit repeatable: the same 279-token prompt, prefilled again and again in one process, gave a different prefill-to-decode state about 1 time in 1,000 on the sixteenth-round build (6 in 5,550 with the defaults, over three sessions; the rate drifts between sessions) and about 1 time in 25 on the fifth-round build. Per-op output checksums put the first difference in the expert gate/up kernel (`MUL_MAT_ID_NX+SWIGLU`) with identical inputs. The cause was not found, and no switch tested removes it: in interleaved runs on a clean build, turning off the tenth-round activation-row DMA (`GGML_HEXAGON_MMID_BAG=0`) gave 7 deviations in 4,000 prefills against 2 in 4,000 with the defaults; flushing output cache lines (`GGML_HEXAGON_DST_FLUSH=1`) gave 3 in 1,000; and an experimental sync after every matrix-unit job, a deeper expert pipeline (`GGML_HEXAGON_MMID_DEPTH=3`) and pushing the activation rows only at each segment start each still deviated. Running each matrix-unit job alone (`GGML_HEXAGON_MMID_DIAG=1`) gave 0 in 1,900, too few to tell at this rate. The eighteenth round found that the kernel itself is nondeterministic in the step that DMA-gathers a new segment's activation rows while it scatters the previous output, and reordered that step (`GGML_HEXAGON_MMID_SCAT_FIRST`); in a check that re-runs every expert op six times this took deviations from 6 in 1,190 to 0 in 1,105, but the hardware cause is unknown and a natural-prefill count large enough to confirm the fix has not been done. The sixteenth-round work-queue race is not the cause either: the fifth-round build with that fix still deviated (15 in 400), and widening the race window changed nothing. This is what made LFM2.5 speculative decoding with 4-token n-gram drafts on the split route give different text in about 1 run in 8 on earlier builds (1 in 16 on the fifth-round build in this check). In those runs the state handed from the NPU to the CPU differed, while CPU decoding was deterministic given the state (`trilane-spec` with `TRILANE_DET_HASH=1` prints both hashes). On the sixteenth-round build, 69 of 69 such runs and 37 of 37 full LFM2.5 perplexity passes (24 chunks) were identical. Whether the eighth-round perplexity deviations (2 of 23 passes, one window each) came from the same effect is not known.
- The fork's NPU kernels shift LFM2.5's logits slightly against stock (KLD 0.006; perplexity +0.66% ± 0.3% on 8 wikitext chunks, +0.35% on 16). Disabling the new fusions one at a time does not remove the shift, so the cause is unresolved. Qwen3.5-2B is unchanged (perplexity ratio 1.0008). The causal key-block skip changes LFM2.5's greedy text after a few tokens (a no-op update that rounds fp16 differently; perplexity identical; `GGML_HEXAGON_FA_KV_SKIP=0` restores it).
- The NPU gated-delta-net kernel, unchanged from upstream, fails 16 of 43 `test-backend-ops` cases (NMSE up to 6e-2 against a 1e-7 threshold, varying run to run) in every build tested. Its effect on output quality vs the CPU has not been measured.
- A second process holding an NPU session, even an idle one, slowed another process's NPU work 2-4×, and overlapping NPU jobs have failed with dspqueue errors. Run one NPU process at a time.
